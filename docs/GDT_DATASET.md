# GD&T dataset and evaluation

How the GD&T recognizer is measured, what the current numbers do and do not
mean, and the workflow for annotating real drawings.

## There is no real labelled set yet

The repository already has `backend/benchmarks/documents/` — three drawings
with ground truth for the *dimension values* a sheet carries. Those fixtures
have no symbol classes and no symbol boxes, so they cannot score symbol
recognition. There is no labelled GD&T set here, and inventing accuracy
figures for real scans would be worse than having none.

What can be built honestly is a **generator**:
`backend/benchmarks/gdt_synthetic.py` draws frames and callouts from the same
geometry the registry describes, so every symbol's identity, bounding box and
field values are known exactly rather than annotated by hand.

### What it measures, and what it does not

**It measures**

- whether the classifier separates the symbols from each other
- how recognition degrades under blur, noise, skew and low resolution
- whether frame segmentation finds the right compartments
- whether field parsing and datum precedence are right
- localisation quality (IoU) and end-to-end latency

**It does not measure**

- performance on real CAD fonts — scenes are drawn with Hershey and with
  procedural templates
- scanner artefacts this generator does not model
- symbols touching dimension lines in ways not simulated here
- any real-world class balance: every class appears a handful of times, where
  a real sheet may carry forty diameters and one cylindricity

**A number from this suite is a regression baseline and a floor, never a claim
about field accuracy.** Closing that gap needs the annotation workflow below.

## Running it

```bash
cd backend
PYTHONPATH=. .venv/bin/python scripts/run_gdt_eval.py                  # symbols only
PYTHONPATH=. .venv/bin/python scripts/run_gdt_eval.py --ocr --save     # + frame fields
PYTHONPATH=. .venv/bin/python scripts/run_gdt_eval.py --conditions clean,scan
```

`--ocr` loads PaddleOCR so frame *fields* are scored too. Without it, frames
are still found and their symbols classified, but compartments have no text,
so tolerance and datum fields report as declined rather than wrong. Symbol
numbers do not change between the two modes.

Every scene takes a seed and is reproducible. A benchmark that moves when
nothing changed is worthless as a regression signal.

## Scenes

| Scene | Covers |
|---|---|
| `symbol_grid` | Every templated symbol once — per-class classification |
| `frames` | Feature control frames with varied fields and datum counts |
| `composite_frame` | A two-segment composite position control |
| `dense` | Frames packed close together, datum features on a surface line |
| `confusables` | The registry's own `confusable_with` pairs, side by side |
| `small_modifiers` | Circled modifiers at note size — the resolution floor |

Conditions: `clean`, `blurred`, `noisy`, `low_res`, `skewed`, `scan`,
`poor_scan`. `scan` and `poor_scan` compose blur, noise, skew, downscaling and
JPEG artefacts.

Localisation is **not** scored under `skewed` and `poor_scan`: the page is
rotated, so axis-aligned truth boxes no longer describe the symbols, and an
IoU there would measure the rotation rather than the detector. The report says
so rather than quietly reporting a low number.

## Metrics, and why macro is the headline

Reported per class: precision, recall, F1, mean IoU, and how often a correct
detection was nonetheless flagged ambiguous.

**Read macro, not micro.** The brief is explicit that rare symbols must not be
hidden behind common ones, and on a drawing the class balance is extreme. A
micro-average would mostly be a report on how well the recognizer reads `Ø`.

Also reported:

- **Declined rate** — how often the system refused to name something it
  detected. A recognizer that answers "unknown" to everything has perfect
  precision and is useless; one that guesses confidently on everything has
  good recall and is dangerous. Both numbers are published so the trade is
  visible rather than tuned away.
- **False-positive rate**.
- **Top-k recall** — recall counting a miss as a hit when the right class was
  offered among the alternatives. Reported *beside* strict recall, never
  instead of it: offering two candidates is useful to an operator who will
  arbitrate and useless to an automated consumer that needs one answer.
  Published as both macro and micro, each labelled, because mixing the two is
  how a report ends up claiming a "top-k recall" below its own recall.
- **Frame field accuracy** per field, with declines counted separately from
  errors.
- **Datum sequence accuracy** — the whole ordered sequence, not per letter.
  Getting `A B C` in the wrong order is wrong, not two-thirds right.
- **Latency** per page.

## Measured baseline

Generated by `scripts/run_gdt_eval.py --ocr --save`, pooled across all six
scenes, 43 classes with support. Stored in
`backend/benchmarks/results/gdt_baseline.json`.

| Condition | macro P | macro R | macro F1 | top-k R | declined | FP rate | frames | ms/page |
|---|---|---|---|---|---|---|---|---|
| clean | 0.845 | 0.859 | 0.819 | 0.928 | 41.5% | 13.8% | 13/13 | 3159 |
| blurred | 0.834 | 0.825 | 0.785 | 0.902 | 38.3% | 18.1% | 13/13 | 3914 |
| noisy | 0.863 | 0.853 | 0.830 | 0.922 | 41.3% | 12.0% | 13/13 | 5352 |
| low_res | 0.804 | 0.806 | 0.778 | 0.882 | 44.1% | 20.4% | 12/13 | 4335 |
| skewed | 0.697 | 0.717 | 0.677 | 0.787 | 41.7% | 33.3% | 13/13 | 3229 |
| scan | 0.801 | 0.810 | 0.768 | 0.880 | 40.4% | 21.3% | 12/13 | 5095 |
| poor_scan | 0.657 | 0.609 | 0.595 | 0.661 | 54.9% | 41.8% | 3/13 | 4276 |

Isolating classification from detection, on `symbol_grid` alone (clean): macro
F1 **0.822**, strict recall 0.860, top-k recall 0.953, mean IoU **1.000**.

An earlier baseline recorded materially lower figures (clean macro F1 0.690,
`confusables` at 0.000). That was a stale artifact, not a change in the
recognizer: `find_glyph_boxes` sized its upper bound as a fraction of the
*region*, which collapses to a few pixels on the small scenes, and the
absolute floor that fixes it landed after that baseline was written. It is a
good argument for regenerating the file in the same change as any detector
edit.

### Reading these numbers honestly

**Precision and recall sit close together, and the declined rate is high.**
That is the designed trade: the system declines rather than guesses, so a
degraded input moves a result to `ambiguous` rather than to a different
symbol. Across every condition the detector produced no confident *wrong*
answer in the unit suite. The declined rate of roughly 40% is the price, and
it is reported rather than tuned away.

**The gap between strict and top-k recall is mostly the identical-glyph
pairs.** Counterbore/spotface, profile-of-a-line/arc length,
diameter/spherical-diameter and datum-triangle/datum-feature-symbol are the
same mark; shape cannot separate them and the system says so. Those count as
both a false negative and a false positive under strict scoring, which is
correct — the system did not commit to the right answer — but it is a
different failure from "saw nothing".

**Weakest classes on clean** (see `gdt_baseline.json` for the current
per-class table), and why:

| Class | F1 | Reason |
|---|---|---|
| `datum_feature_symbol` | 0.00 | Reported as `datum_triangle` without a readable letter |
| `spherical_diameter` | 0.00 | Same glyph as `diameter`; the `S` is text |
| `spotface` | 0.00 | Same glyph as `counterbore`; only `SF` separates them |
| `total_runout` | 0.40 | Two arrows against `parallelism`'s two strokes |
| `datum_triangle` | 0.40 | Over-reported where a datum feature symbol was meant |
| `mmc` | 0.50 | Drawn at ~20px in frames — below the resolution floor |
| `parallelism` | 0.50 | Loses to `total_runout` on the confusables scene |

Three of those seven score zero because they are the *same glyph* as another
symbol, and all three put the right answer in their alternatives — they are
the top-k gap, not blindness.

28 of 43 classes reach F1 1.00 in the pooled clean run, against 33 of 43 on
`symbol_grid` alone. The difference is the `confusables` scene, which is
*entirely* made of pairs the registry predicts will be confused — it is meant
to be hard, and pooling it in drags the aggregate down on purpose.

**`poor_scan` is where it falls over**: frames drop to 3 of 13. That condition
composes 5px blur, σ=30 noise, 3° skew, 0.65× downscaling and JPEG quality 40.
The honest reading is that the frame path needs a better-quality render than
that, which is what the frontend's `GDT_RENDER_SCALE` re-render provides.

### Frame fields, clean, with OCR

| Field | Correct | Declined |
|---|---|---|
| Characteristic symbol | 13/13 (100%) | 0 |
| Tolerance value | 13/13 (100%) | 0 |
| Diametral zone | 13/13 (100%) | 0 |
| Material condition | 2/13 (15%) | 11 |
| Datum sequence | 8/13 (62%) | — |

The material-condition number is the resolution floor, not a classifier
failure: at the 38–44px frame heights these scenes draw, a circled modifier is
about 20px with a 10px letter inside. The system reports those `unreadable`
rather than `absent`, which is the important part — `absent` would be read as
RFS. Re-rendering the same frames larger fixes it:

| Frame height | Fields correct |
|---|---|
| 44 px | 92% |
| 66 px | 100% |
| 88 px | 100% |

## Dataset specification for real drawings

The synthetic suite cannot become a field-accuracy claim. This is what a real
set needs.

### Coverage targets

The brief's list, each needing enough instances to produce a per-class number
worth reading (≥ 20 instances per class, ≥ 5 drawings per condition):

- clean CAD-generated drawings (vector PDF)
- low-resolution scans (≤ 200 dpi)
- blurred and noisy drawings
- rotated or skewed pages
- dense feature control frames
- small modifiers at note size
- similar-looking symbols on one sheet
- legacy and standards-specific notation (pre-2018 ASME, ISO)
- symbols touching dimension or extension lines
- multiple symbols close together

Record for every drawing: source standard and revision **when stated on the
sheet**, units, rendering dpi, and provenance. Where the standard is not
stated, record that it is unknown — do not infer it from the symbols present,
which would make the standards check circular.

### Annotation schema

One JSON file per drawing, beside the image, mirroring
`gdt_synthetic.Scene.truth()` so the existing scorer reads it unchanged:

```json
{
  "name": "47630-sheet1",
  "source": "Docs/47630.pdf",
  "dpi": 300,
  "condition": "clean",
  "standard": "ASME Y14.5-2009",
  "standard_source": "stated in title block",
  "units": "inch",
  "symbols": [
    {
      "symbol_id": "position",
      "bounding_box": {"x": 120, "y": 240, "width": 18, "height": 18},
      "frame_id": "fcf-1",
      "role": "characteristic"
    }
  ],
  "frames": [
    {
      "id": "fcf-1",
      "bounding_box": {"x": 110, "y": 232, "width": 180, "height": 34},
      "symbol_id": "position",
      "tolerance": 0.05,
      "diameter_zone": true,
      "material_condition": "mmc",
      "datums": ["A", "B", "C"],
      "segment_index": 0,
      "composite_id": null
    }
  ]
}
```

Rules:

- `symbol_id` must exist in the registry. `GET /gdt/registry` is the list.
- Boxes are the symbol's **ink**, not its cell. The two differ by about 28%
  per axis, and annotating cells makes IoU measure the margin rather than the
  detector — this was a real bug in the generator and it depressed mean IoU
  from 1.000 to 0.562.
- `material_condition` is `null` only when the frame genuinely has none.
  Unreadable-on-the-sheet is a separate annotation note, not a `null`.
- Record datums in **precedence order**.

### Workflow

1. Render the drawing at a recorded dpi, keeping the file as the source of
   truth; the annotation references it rather than copying it.
2. Pre-label with the recognizer: `POST /ocr/gdt-symbols` and save the
   response. It is faster to correct boxes than to draw them.
3. Correct in the app — the GD&T panel's reclassify / "not a symbol" /
   confirm actions are the correction UI, and they already record exactly the
   fields this schema needs.
4. Export `GET /gdt/corrections?document_hash=…` and fold them into the
   drawing's truth file.
5. **Have a second annotator review any symbol the first marked ambiguous.**
   The identical-glyph pairs need a human to look at the surrounding context,
   which is the same information the recognizer uses and the same place it
   can be wrong.
6. Record inter-annotator disagreement. A class people disagree about is not
   a class to hold a model to without resolving it first.

### Using corrections as a growing set

`GET /gdt/corrections/summary` reports which pairs are actually confused in
service. That is a better guide to what to improve than any synthetic scene,
because it reflects the drawings this deployment actually sees.

Corrections carry a document hash, never image data, so they stay inside the
same retention posture as the checksheet store. Before folding corrections
into a shared dataset, confirm the drawings may be retained for that purpose —
a correction references customer geometry even when it does not contain it.

## Keeping the baseline honest

- Re-run `--save` after any change to detection, templates or thresholds, and
  compare per class. An aggregate that holds steady while a rare class
  collapses is the failure this report exists to catch.
- A moved number with no code change means the suite stopped being
  deterministic — fix that before trusting anything else in it.
- When a real labelled set exists, report it **separately**. Pooling synthetic
  and real results produces a number that describes neither.
